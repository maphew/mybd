### #5065 — halaprix: fix(github): include bead metadata in synced issue bodies

**Verdict:** needs-changes

**CI:** No checks reported on branch fix/github-sync-body-4307 — workflows have not run (likely awaiting first-time-contributor approval). GitHub reports mergeable=MERGEABLE against main; local main shows no drift in the touched hunks of internal/github/mapping.go, tracker.go, or cmd/bd/github.go.

PR #5065 implements items 1 and 2 of gastownhall/beads#4307: it renders a delimited `<!-- bd-github-sync: start/end -->` block into pushed GitHub issue bodies carrying the bead ID marker plus dependency/dependent tasklists, strips that block on pull so local descriptions stay clean, and wires a new `PushHooks.FormatDescription` for `bd github sync`. The approach is sound and matches the existing Linear precedent (`cmd/bd/linear.go:763` + `internal/linear/mapping.go:26`), scope is disciplined (comment mirroring correctly excluded), and the `CreateIssue` change to use the mapper's title/body is a real latent-bug fix. However the pull-side ID extraction trusts an unvalidated, unscoped marker anywhere in an externally-authored issue body and feeds it straight into the engine's local-ID matching, which can silently overwrite an unrelated local bead; and the hook is wired into only one of the two GitHub push entrypoints, so `bd github push` erases the tasklists that `bd github sync` writes.

**Overlap:** Direct conflict with open PR gastownhall/beads#4329 ("fix(github): content-based dedup on push to stop re-PATCHing every issue (#4214)"), which the author acknowledges in the PR body but only as "adjacent". It touches the same three files plus internal/tracker/engine.go, and its `PushFieldsEqual` (`local.Description != remote.Body`) and `PushContentHash(local.Description)` become permanently unequal once #5065 renders a managed block into remote bodies — combining them as-is reintroduces #4214. No other open PR targets #4307 or the marker/tasklist scope (searched open PRs touching internal/github/mapping.go).

**Findings:**

- **blocker** — internal/github/mapping.go, new func `ExtractBDIDFromGitHubSyncBlock` (added after line 199): despite the name it does `strings.Index(body, "<!-- bd:")` over the WHOLE body — not scoped to the `<!-- bd-github-sync: start/end -->` delimiters — and applies no ID-format validation (it returns the first whitespace field that isn't `sync=`). `GitHubIssueToBeads` (mapping.go:123) then assigns that string to `Issue.ID`. In the engine, internal/tracker/engine.go:436 uses it to look up `localByID`, and cmd/bd/github.go:495's `GenerateID` hook only fills IDs that are empty. Consequences: (a) an arbitrary externally-controlled string becomes a newly created local bead's primary ID; (b) a GitHub issue whose body contains `<!-- bd: bd-abc123 -->` will be matched to the unrelated existing local bead `bd-abc123`, and internal/tracker/engine.go:501 `buildPullIssueUpdates` then overwrites that bead's title, description, priority, status, issue_type and assignee and rewrites its external_ref — silent data loss. The default issue prefix is `bd` for every project (cmd/bd/github.go:481), so cross-project ID collision when importing issues from another beads-synced repo is a realistic, non-adversarial path. Fix: find the start/end delimiters first and only parse the marker inside them; require the extracted ID to match the local issue prefix + ID pattern; ignore the marker entirely when the issue's repo is not the configured sync repo.
- **major** — cmd/bd/github.go:423 wires `engine.PushHooks = buildGitHubPushHooks(ctx)` for `runGitHubSync` only. `runGitHubPush` at cmd/bd/sync_push_pull.go:604 constructs its own engine with NO PushHooks. Because `BeadsIssueToGitHubFields` now falls back to `RenderGitHubIssueBody(issue, nil, nil)` when the description carries no marker, `bd github push` will overwrite a remote body previously written by `bd github sync` with a block containing no dependency sections — the two commands fight and silently destroy the tasklists. Fix: set `engine.PushHooks = buildGitHubPushHooks(ctx)` in `runGitHubPush` too (and add a test asserting both entrypoints render identical bodies).
- **major** — Integration conflict with open PR gastownhall/beads#4329 ("content-based dedup on push", same files: internal/github/mapping.go, internal/github/tracker.go, cmd/bd/github.go). #4329 compares `local.Description != remote.Body` and hashes `local.Description` in `PushContentHash`. Once #5065 renders the sync block into the remote body, local description and remote body can never be equal, so the dedup would never fire and every issue gets re-PATCHed on every push — precisely the bug #4214 that #4329 exists to fix. Additionally the tasklist content depends on dependency edges and on deps acquiring external refs, so a hash over `local.Description` alone is stale even after stripping. Whichever PR lands second must reconcile: compare `RenderGitHubIssueBody(...)` output against `remote.Body`, or strip the block from both sides and hash the dependency set separately.
- **major** — cmd/bd/github.go, new `buildGitHubPushHooks`: `if depErr != nil { dependencies = nil }` / `if dependentErr != nil { dependents = nil }` silently swallows storage errors. A transient DB failure produces a body with the dependency sections removed, which is then PATCHed over the remote issue — destroying the tasklists with zero user-visible signal. Fix: on error either return `issue.Description` unchanged (skip re-render, leaving the remote body alone) or surface it via `engine.OnWarning` so the degraded push is visible, consistent with how the engine reports partial-success warnings at internal/tracker/engine.go:986.
- **major** — internal/github/mapping.go, new `githubIssueNumberFromRef`: it takes `strings.LastIndex(ref, "/issues/")` and emits `#<n>` for any ref containing that substring. A dependency whose ExternalRef points at a different repo (`github.com/other/repo/issues/12`), a different host (GitLab `https://gitlab.com/g/p/-/issues/12`), or GH Enterprise will render as a bare `#12`, which GitHub resolves against the CURRENT repo — silently linking to a completely unrelated issue. Fix: only emit `#n` when the ref's host/owner/repo match the configured `MappingConfig`/tracker repo (the tracker already has `IsExternalRef`/`ExtractIdentifier` at internal/github/tracker.go:170-186); otherwise emit the full URL.
- **minor** — cmd/bd/github.go `buildGitHubPushHooks` issues two store queries per pushed issue (`GetDependenciesWithMetadata` + `GetDependentsWithMetadata`). For the 690-issue repo described in #4307 that is ~1380 embedded-Dolt round trips per push. Linear's equivalent hook (`linear.BuildLinearDescription`, internal/linear/mapping.go:26) is pure. Fix: prefetch once into a closure-scoped map guarded by `sync.Once`, mirroring the `loadPushLabelCache` pattern at cmd/bd/linear.go:748-762.
- **minor** — internal/github/mapping.go `appendGitHubTasklistSection` always writes `- [ ]`, never `- [x]`, regardless of whether the dependency issue is closed. Since these are real GitHub checkboxes, any user with write access toggling one mutates the remote body; the next push silently reverts it. At minimum render `[x]` for `types.StatusClosed` deps so the checkbox reflects reality instead of inviting manual toggling.
- **minor** — internal/github/mapping.go `RenderGitHubIssueBody`: the section headings are blocking-flavoured ("Dependencies" / "Blocked by this issue") but the underlying queries return ALL edge types. A `parent-child` dependent renders under "Blocked by this issue" labelled "child", and `discovered-from`/`related` edges land there too — semantically wrong. Fix: group by dependency type, or use neutral headings ("Depends on" / "Referenced by").
- **minor** — internal/github/mapping.go:155-158: the `strings.Contains(body, "<!-- bd-github-sync: start -->")` sniff that preserves a pre-rendered body is a fragile mapper/hook coupling. If a local description ever legitimately contains the marker (hand-edited bead, JSONL import from a repo synced by a different bd version, user paste), push will send that stale block — stale bead ID and stale dependency list — verbatim and forever, since the mapper never refreshes it. The Linear integration avoids this by keeping the tracker dumb (`internal/linear/tracker.go:207`: "Use issue.Description as-is: the sync engine's FormatDescription hook..."). Simpler alternative: rely solely on the hook (wired into both entrypoints per the finding above) and drop the mapper-side render + sniff — that deletes ~10 lines and removes the staleness class entirely.
- **minor** — internal/github/mapping.go `RenderGitHubIssueBody` emits the full block even when `issue.ID` is empty AND there are no dependencies, turning an empty/plain description into three lines of pure marker noise (`start` / `## Beads` / `end`) on every synced issue. Guard: skip the block when there is no ID and no edges.

**CI:** Not run. `gh pr checks 5087` reports "no checks reported on the 'fix/uow-init-only-create' branch", and the check-runs API returns total_count 0 for both head d2b24c1 and the parent 8a210de. PR #5087 is the cmd/bd policy half of a two-PR stack (with #5086) that fixes gastownhall/beads#5079: the proxied-server open path in `internal/storage/uow/dolt_sql_provider.go` unconditionally issues a bare `CREATE DATABASE` on every open, so least-privilege accounts cannot even run `bd list`. The approach — probe with `SHOW DATABASES` first, then gate creation behind a new `WithCreateIfMissing` option that only `bd init --proxied-server` sets true — is exactly what the issue asked for and faithfully mirrors the direct stack's existing `databaseExistsOnServer` + `dolt.Config.CreateIfMissing` guard. I verified the bug still exists on `upstream/main` (dolt_sql_provider.go:105 always attempts CREATE on the first attempt), that all three `newProxiedServerUOWProvider` call sites are covered, that `bd init` and `db-proxy-child` do not go through the `main.go` PersistentPreRunE proxied branch (so the `false` there cannot break init), and that every proxied integration test seeds via `bd init`. The mechanism is correct; my findings are about the user-facing error text, the option's default polarity, and one collateral command.

**Overlap:** Two overlaps. Merging #5087 alone lands both and makes #5086 redundant; merging #5086 first (especially squashed) will force a rebase of #5087. Pick one order deliberately, ideally landing #5087 and closing #5086 as absorbed with attribution. (2) #4303 ("db-proxy connection pooling (opt-in) + proxied-server external deploy path") touches all four of the same files — cmd/bd/uow_factory.go, internal/storage/uow/dolt_sql_provider.go, doltserver_provider.go, external_doltserver_provider.go — including the constructor signatures this PR extends with variadic options. The author flags this and offers to rebase whichever lands second; #4303 is much larger, so landing this small fix first is the lower-friction order. Both PRs are currently MERGEABLE against main.

**Findings:**

- **major** — internal/storage/uow/dolt_sql_provider.go (new guard, `return backoff.Permanent(fmt.Errorf("uow: database %q not found on Dolt server; run 'bd init' to create it", database))`) — the hint points at `bd init`, which contradicts this repo's established recovery guidance for exactly this condition. The direct stack's equivalent error, `databaseNotFoundError` at /var/home/matt/dev/mybd/bd-main/internal/storage/dolt/errors.go:132, and `handleFreshCloneError` at /var/home/matt/dev/mybd/bd-main/cmd/bd/main_errors.go:27 both steer the user to `bd bootstrap` and explicitly say "Use bd init only when creating a brand-new project with no existing .beads data" (GH#2327: the Dolt DB is runtime state not in git, so branch switch / fresh clone is the dominant cause). This matters more here than usual because #5087 converts a previously-silent create into a hard failure — a proxied-server user who switches branches or freshly clones now hits this message first, and following it runs `bd init` on an existing project. Fix: change the hint to `run 'bd bootstrap' (or 'bd init' for a brand-new project)`, or better, export a typed `uow.ErrDatabaseNotFound` and have cmd/bd render the existing rich message.
- **minor** — internal/storage/uow/dolt_sql_provider.go, `newUOWProviderOptions` defaults `createIfMissing: true` — the inverse polarity of the direct stack's `dolt.Config.CreateIfMissing` (a plain bool defaulting to false, opt-in; /var/home/matt/dev/mybd/bd-main/internal/storage/dolt/store.go:345, with every creating call site setting it explicitly, e.g. cmd/bd/init.go:1132 "bd init is the only path that should create databases"). Defaulting true was justified for #5086 standing alone, but once #5087 lands and all three call sites are explicit, the safe default is false: any future call site then fails closed instead of silently regaining implicit create. Suggested fix: flip the default to false in this PR's commit and drop the now-redundant `WithCreateIfMissing(false)` at main.go:1329 and dolt_clean_databases_proxied_server.go:11, keeping only the explicit `true` at init_proxied_server.go:148.
- **minor** — cmd/bd/dolt_clean_databases_proxied_server.go:11 — passing `WithCreateIfMissing(false)` makes `bd dolt clean-databases` unusable in the one scenario where you most want it: the configured database was dropped/corrupted and stray `beads_test*`/`testdb_` databases are left behind. `cleanDatabases` never touches the configured database — it runs its own `SHOW DATABASES` over the connection (cmd/bd/dolt_clean_databases.go:32) and only drops names matching `staleDatabasePrefixes` (cmd/bd/dolt.go:1253) — yet the provider open still probes, USEs and migrates the configured DB just to get a `*sql.Conn`. The correct long-term fix is a provider open for this path that skips `initSchema` entirely; at minimum note the behavior change, since previously this command silently created (and migrated) the database in order to clean others.
- **minor** — No test covers the policy wiring that is the entire content of this PR's own commit. The two new tests live in #5086's commit and exercise the storage option; nothing asserts that main.go/clean-databases pass false and init passes true. Additionally both new tests are docker-gated — `testutil.StartIsolatedDoltContainer` calls `t.Skipf` when Dolt/docker is unavailable (/var/home/matt/dev/mybd/bd-main/internal/testutil/testdoltserver.go:187) — so they will skip in most lanes. A cheap regression lock would be a table test over the three call sites, or a proxied integration test that removes the database server-side and asserts the next `bd list` fails without recreating it.
- **minor** — The not-found condition is a bare `fmt.Errorf` string with no sentinel, and it arrives at the user triple-wrapped: cmd/bd/main.go:1329 renders `failed to open uow provider: uow: init schema: uow: database "beads" not found on Dolt server; run 'bd init' to create it`. The non-proxied path deliberately unwraps and re-renders this class of error (main.go:1388 `handleFreshCloneError`). Exporting `var ErrDatabaseNotFound = errors.New(...)` and wrapping with `%w` would let the proxied branch give the same treatment, and would also let #4303 and future callers classify it.
- **nit** — internal/storage/domain/db/ddl.go, new `DatabaseExists` — exact `name == database` comparison. MySQL/Dolt database-name matching is not reliably case-sensitive across platforms; previously a case-mismatched configured name still resolved via CREATE→1007→USE, whereas now with create disabled it yields a spurious not-found. Low risk and it is consistent with the direct stack's `databaseExistsOnServer` (internal/storage/dolt/store.go:1958), which does the same, so this is a pre-existing convention rather than a new defect — worth at most a comment or a shared helper.
- **nit** — internal/storage/domain/db/ddl.go — `DatabaseExists` does not call `quoteIdentifier` (correct: the name is never interpolated). Side effect: for an invalid `dolt_database` name like `beads-x`, the user now gets "not found on Dolt server; run 'bd init'" instead of the previous `invalid identifier: "beads-x"` from `CreateDatabase`, and the suggested `bd init` will then fail with the real error. Cheap improvement: validate the identifier in `DatabaseExists` and return the invalid-identifier error early.
- **nit** — Duplication: the new `ddlSQLRepository.DatabaseExists` is line-for-line the same logic as `databaseExistsOnServer` (internal/storage/dolt/store.go:1958), differing only in taking a `db.Runner` instead of a `*sql.DB`. Not worth blocking on — the signatures genuinely differ — but a follow-up could have the direct stack delegate to the `db` package so the two stacks cannot drift.

**Recommendation:** Land it after changing the not-found hint from `bd init` to `bd bootstrap` (matching internal/storage/dolt/errors.go:132 and cmd/bd/main_errors.go:27) — a one-line maintainer edit — and preferably flip the `createIfMissing` default to false now that all three call sites are explicit; close #5086 as absorbed and land ahead of #4303.

### #5089 — steveyegge: feat(dolt): configurable shared-pool per-I/O read/write deadlines

**Verdict:** approve-with-nits

**CI:** green — all checks pass (Build Embedded Dolt, Lint, doc freshness x3, contract corpus, differential regression, 20 embedded + 15 proxied Dolt shards, storage conformance); no failures or pending.

PR 5089 makes the shared Dolt pool's hardcoded 10s per-I/O ReadTimeout/WriteTimeout (buildServerDSN, store.go:1736-1737 on main) configurable via Config fields, BEADS_DOLT_POOL_{READ,WRITE}_TIMEOUT env vars, and dolt.pool-{read,write}-timeout config.yaml keys, with defaults deliberately unchanged. The implementation mirrors the sibling dolt.max-conns resolution block (open.go:287-302) exactly, the timeoutFromEnv -> parseTimeout extraction is behavior-preserving, and both live open paths (open.go:100, open.go:130) run applyResolvedConfig so the knob actually reaches every server-backed store. Test coverage is proportionate (DSN table test, parseTimeout table test, two applyResolvedConfig subtests) and CI is fully green. The fix matches the stated problem; findings are polish, not correctness blockers.

**Overlap:** Same author has two adjacent open PRs against internal/storage/dolt/store.go: #5090 (routes recompute-blocked onto the long-timeout connection — addresses the *same* bd-bn8jo incident cited in this PR body, complementary rather than redundant, hunks at ~3438/3470 so no textual conflict) and #5052 (backup on an undeadlined one-shot connection, which refactors execWithLongTimeoutNoTx into a shared `oneShotConn(readTimeout)` helper at the ~1604-1622 region). #5052's hunk is adjacent to 5089's buildServerDSN hunk but does not overlap it; if #5052 lands first, the finding above about clamping the 5m long-timeout downward should be applied inside `oneShotConn` instead of at three call sites. #4473 and #4303 (connection pooling) touch the same subsystem conceptually but not these lines.

**Findings:**

- **minor** — internal/storage/dolt/open.go (new hunk, ~line 304): the block comment says "env var > config.yaml > caller override > default" but the code checks `cfg.PoolReadTimeout == 0` first, so the actual order is caller > env > config.yaml > default — which is what the PR body claims. The wrong text is copied verbatim from the pre-existing stale comment on the max-conns block (open.go:287 on main). Fix: write "caller override > env var > config.yaml > default" in the new comment (and optionally correct line 287 in the same pass), since these comments are the only documentation of precedence for the knob.
- **minor** — internal/storage/dolt/store.go:1754, :1781, :3273 (main line numbers): execWithLongTimeout, execWithLongTimeoutNoTx and openLongTimeoutConn re-parse s.connStr and set `cfg.ReadTimeout = 5 * time.Minute` unconditionally. With this PR a deployment that sets PoolReadTimeout above 5m (e.g. `10m` on the load-avg-81 host the PR body describes) silently gets its long-timeout paths *lowered* to 5m — the opposite of the operator's intent, and invisible. Fix: clamp upward instead, e.g. `if cfg.ReadTimeout < longConnReadTimeout { cfg.ReadTimeout = longConnReadTimeout }`. (Related pre-existing gap, out of scope: those paths never raise WriteTimeout, so a large push still writes under the pool's deadline.)
- **minor** — docs/reference/configuration.md:112 already documents the sibling knob (`| dolt.max-conns | — | BEADS_DOLT_MAX_CONNS | 10 | Connection pool size |`) in a hand-maintained table; scripts/check-doc-freshness.sh:22 only pins that file to cmd/bd/main.go, cmd/bd/config.go and internal/configfile/, so nothing generates or regenerates it. The PR body's rationale ("No docs edit: ... the knob reaches the site at the next release regeneration") does not hold for this table — the two new keys will be undiscoverable indefinitely. Fix: add two rows next to dolt.max-conns with the 10s defaults and the BEADS_DOLT_POOL_{READ,WRITE}_TIMEOUT env names.
- **nit** — internal/config/config.go:165-169 sets SetEnvPrefix("BD") + SetEnvKeyReplacer("."->"_", "-"->"_") + AutomaticEnv, so `config.GetString("dolt.pool-read-timeout")` also resolves BD_DOLT_POOL_READ_TIMEOUT. The knob therefore has two env spellings with different precedence (BEADS_* wins, BD_* is only consulted at the config.yaml tier). This already applies to dolt.max-conns so it is not new, but it is worth one sentence in whatever docs row lands so operators do not set BD_* and wonder why the BEADS_* tier ignores it.
- **nit** — internal/storage/dolt/open.go: the config.yaml tier uses only `config.GetString(...)`, which is empty for library consumers that never call config.Initialize(). The auto-start resolution a few lines below (open.go:145-148) handles exactly this with a `config.GetStringFromDir(beadsDir, ...)` fallback. Consistent with the max-conns sibling, so acceptable as-is; adding the GetStringFromDir fallback would be a one-line improvement over copying the sibling's limitation.

**Recommendation:** Approve and merge after the author fixes the inverted precedence comment and adds the two rows to docs/reference/configuration.md; the 5m long-timeout clamp can be a follow-up bead (coordinate with #5052's oneShotConn refactor).
