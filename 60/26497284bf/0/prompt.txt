## 1. Design assessment per slice

### Slice 1 — `claim_fence` (commit `a252ad2b1`): **independently valuable, keep it**

This is the part worth fighting for. Upstream already shipped a row-version CAS in #4911 (`ExpectedVersion`, `CheckVersionInTx`, `ErrVersionMismatch`) — but that token *is* `row_lock`, which every content mutation rewrites. A guard on `row_lock` therefore fails on any unrelated edit (a note append, a metadata merge). `claim_fence` fills a real gap: a token that moves **only** on ownership transitions, so an orchestrator can hold a stable ownership snapshot across content churn. That semantic is not covered by anything upstream, and the PR argues it well.

The Dolt cell-merge reasoning is also correct and worth crediting explicitly: a bare monotonic counter would silently cell-merge under Dolt (two N→N+1 bumps write identical values), and the paired `row_lock` rewrite is what forces serialization. `fence.go:16-25` states it and `fence_invariant_test.go:30` enforces it at the AST level. That is the right instinct.

Contentious sub-point: **what bumps**. `fence.go:70-115` documents "ownership transitions only," but `claim.go:105-118` bumps unconditionally on every successful claim — including a same-actor re-claim of an open-but-already-assigned-to-me row. Meanwhile `fence.go:61-68` (`UpsertFenceAssignments`) goes to real trouble to *avoid* a spurious bump on a content-only re-import, with a comment explaining why spurious bumps "conflict legitimate outstanding guards." Two paths, opposite policies, one doc. Pick one and test it — see finding S-4.

### Slice 2 — guarded verbs `--if-assignee` / `--if-fence` (commit `267befb7e`): **contentious, needs reconciliation before it can land**

Upstream merged `6e8af8bf8` — *"feat(update): conditional compare-and-set guards --if-assignee/--if-status (bd-wsqvw) (#5008)"* — on 2026-07-24. Its own commit message says the guards were deliberately put on `UpdateIssueOptions` (`ExpectedAssignee`/`ExpectedStatus`, `CheckExpectedFieldsInTx`, `ErrStatusMismatch`) **"rather than minting a parallel interface method — no Storage interface break, decorators pass through unchanged."**

This PR mints a parallel mechanism: `issueops.Guard` carried in a **context value** (`guard.go:53-72`), `storage.PreconditionFailedError`/`ErrPreconditionFailed`, and a different exit code. Concretely:

| | upstream #5008 (merged) | PR #4697 |
|---|---|---|
| flag on `bd update` | `--if-assignee`, `--if-status` | `--if-assignee`, `--if-fence` |
| mismatch exit | **13** (`ExitGuardMismatch`, `cmd/bd/update.go:642`) | **9** (`ExitPreconditionFailed`) |
| meaning of 13 | mismatch | **unsupported path** (`ExitConditionalWriteUnsupported`) |
| transport | options struct, wired through all three write stacks incl. proxied | `context.Context` value |
| typed error | `ErrAssigneeMismatch` / `ErrStatusMismatch` | `PreconditionFailedError` |

`cmd/bd/ownership_guard.go:15-19` says the CAS branch "rebases onto this branch." That assumption is now inverted — the CAS work landed first, so #4697 must rebase onto it.

The context-value transport is also the weaker design on the merits, and the PR's own code shows why: `validateGuardInvocation` (`cmd/bd/ownership_guard.go:73-75`) has to *refuse* guards in proxied-server mode with exit 13, because a `context.Value` cannot cross the UOW process boundary — even though `internal/storage/domain/db/issue.go:180-200` implements guard handling. Upstream's options-struct approach crosses that boundary today.

### Slice 3 — `lease.auto` + `bd lease disarm` (commit `0e05bbb64`): **independently valuable, low controversy**

Small, self-contained, honestly documented (including that `ClearArmedLeasesInTx` cannot distinguish explicit from auto leases and clears both, and that the disarm needs a bounded re-sweep for the read-before-flip window). The `HeartbeatIssueInTx` split — renew vs. arm, `ErrUnleased` on a disarmed store — is the right call. This could be a standalone PR today; its only dependency on slice 1 is incidental.

### Slice 4 — tier-complete leases + `--lease-ttl` + batch renew (commits `10364854c`, `dfa9bbb93`): **contentious on the wisps question**

## 2. Correctness findings

### BLOCKER

**B-1 — `internal/storage/issueops/helpers.go:61-66,107-144`: the import/upsert path no longer writes `row_lock` at all.**

The PR removes `"row_lock"` from `issueUpsertColumns` and replaces the `row_lock` INSERT column (bound to `freshRowLock()`) with `claim_fence` (bound to `issue.ClaimFence`). Net effect on both limbs:

- **Fresh INSERT**: `row_lock` now takes the column default `0`. Every imported row lands with `row_lock = 0`. Two nodes importing the same issue write identical `0` — exactly the silent Dolt cell-merge the invariant exists to prevent.
- **ON DUPLICATE KEY UPDATE**: `row_lock` is now rewritten only by `UpsertFenceAssignments` (`fence.go:61-68`), i.e. *only when the assignee changes*. Base rewrote it unconditionally on any accepted update. So an import that changes **status** (e.g. a newer snapshot that closes the issue) no longer rewrites `row_lock`, and can cell-merge with a concurrent reclaim.

The PR also deletes the comment block at `helpers.go` that documented precisely this ("row_lock rides along because any write that can change status/assignee must rewrite it to collide with a concurrent reclaim/close on the same row"). This is not an upstream-drift artifact — upstream has not touched `helpers.go` since the merge base; the removal is the PR's own.

*Fix:* keep `"row_lock"` in `issueUpsertColumns` and keep `freshRowLock()` in the INSERT arg list; add `claim_fence` as an additional column rather than a substitution. Then let `UpsertFenceAssignments` contribute only the `claim_fence` conditional and drop its `row_lock = IF(...)` limb (it would otherwise fight the unconditional assignment for ordering).

**B-2 — `cmd/bd/ownership_guard.go:20-30` + `cmd/bd/update.go:755`: exit-code contract collision and a duplicate flag registration.**

`registerOwnershipGuardFlags(updateCmd)` at `cmd/bd/update.go:755` registers `--if-assignee` on `updateCmd`; `upstream/main:cmd/bd/update.go:797` already registers `--if-assignee` on the same command. pflag's `AddFlag` panics on redefinition, so a merge that keeps both kills the whole CLI at `init()`. `cmd/bd/update.go` does conflict, so a human will see it — but the resolution is a design decision, not a textual one.

Independently of the panic: after any resolution, `bd update --if-assignee` mismatch exits **13** while `bd unclaim --if-assignee` mismatch exits **9**, and **13** simultaneously means "unsupported path" in the new code. That is an unshippable CLI contract.

*Fix:* adopt upstream's `ExitGuardMismatch = 13` for mismatch on all verbs; pick a fresh unused code for "unsupported" (10–12 are taken by `init_safety.go`).

**B-3 — `internal/storage/schema/migration_repairs.go:29`: the new v54 pre-migration repair breaks the per-step-commit invariant. This is the live CI failure, and it is not flake.**

`TestEmbeddedMigrateConvergesUnderConcurrentInterruptedRetries_4566` fails on the PR head with:

```
worker 1 did not converge: attempt 2: killed pass left a DIRTY working set [issues] at version 54 (per-step commit violated)
worker 0 did not converge: attempt 4: killed pass left a DIRTY working set [issues] at version 55 (per-step commit violated)
```

The **version 54** failures point at `preMigrationRepair`'s new `if m.cursorTable == "schema_migrations" &amp;&amp; version == 54 { return ensureLeaseColumns(...) }`, which issues `ALTER TABLE issues ADD COLUMN ...` and `CREATE INDEX` outside the per-step commit boundary. A killed pass then leaves `issues` dirty at v54. The version-55 failures are the new 0056 ALTER pair hitting the same window.

Sibling repairs (`TestEmbeddedMigrateSelfHealsAfterMidPassFault_4566`, `TestEmbeddedMigrateStepCommitLeavesUntouchedUserDirt_4566`) pass in the same run, so this is specific to the newly added repair path, not the harness.

*Fix:* either bring the repair DDL inside the step's commit, or drop `ensureLeaseColumns` from this PR (see S-1 — it is out of scope anyway, and 0055 immediately drops the columns and index it adds).

### SHOULD-FIX

**S-2 — `internal/storage/sqlbuild/sqlbuild.go:51`: `claim_fence` is put in the wrong column constant.**

```go
const LeaseSelectColumns = `leases.lease_expires_at, leases.heartbeat_at, claim_fence`
```

`IssueBaseColumns` is documented as the list callers qualify with a table alias (`QualifyColumns`); `LeaseSelectColumns` exists *specifically* because its `leases.*` references must **not** be qualified. `claim_fence` is an issues/wisps column and belongs on the qualifiable side. Any query that aliases the main table now emits a bare, unqualified `claim_fence` — and `ReclaimScopeSQL` on current main aliases with `i`. With both `issues` and `wisps` carrying the column, that is an ambiguity waiting for the right join.

*Fix:* append `claim_fence` to `IssueBaseColumns`, or add a third `OwnershipSelectColumns` constant that participates in qualification. Note the scan order constraint: `ScanIssueFrom` scans positionally, and upstream has since added `leases.granted_node` as a third lease column — the merged order must be `…, leases.lease_expires_at, leases.heartbeat_at, leases.granted_node, claim_fence` with the dest list at `scan.go:57` updated to match.

**S-3 — `internal/storage/issueops/scan.go` + upstream `IssueSelectColumnsLite`: the lite-shape parity test will fail after rebase.**

Upstream `132601bfa` added `IssueSelectColumnsLite` and `HeavyDropList`, with a schema-parity test asserting `cols(Lite) ∪ HeavyDropList == cols(Full)` — explicitly so that *"every future column added to IssueSelectColumns must be classified."* `claim_fence` is a new full column and is unclassified. It belongs in **Lite** (small, non-TEXT, read by claim/routing — same rationale upstream gives for keeping `row_lock` there). Purely mechanical, but it will be a red test until done.

**S-4 — `internal/storage/issueops/claim.go:105-118` vs `fence.go:70-115`: the bump policy is documented one way and implemented another.**

`fence.go` says the fence bumps "ONLY on ownership transitions … never by content mutations," and `IsOwnershipTransition` returns false when the assignee is unchanged. `ClaimIssueInTx` bumps unconditionally on any successful claim, including the open-but-already-assigned-to-actor branch of `assigneePredicate` (`claim.go:85`), where the assignee does not change.

This matters more than it looks in a repo like ours: AGENTS.md documents that same-user claims are idempotent, so two sessions of one agent user *cannot* mutually exclude via claims today. Unconditional bump-on-claim would actually **fix** that (session B's re-claim fences out session A's guard) — arguably the single most useful property of the whole feature for the multi-session case. But that is the opposite of what the doc promises, and `UpsertFenceAssignments` implements the opposite policy on the import path with a comment explaining why spurious bumps are harmful.

*Fix:* decide explicitly. If bump-on-every-claim is intended (I think it should be), say so in `fence.go`, drop the "ownership transitions only" framing in favor of "ownership *generation*", and add a test asserting that a same-actor re-claim invalidates an outstanding guard. If not, make the claim bump conditional: `claim_fence = claim_fence + IF(COALESCE(assignee,'') &lt;&gt; ?, 1, 0)`.

**S-5 — `internal/storage/issueops/unclaim.go:72,120`: reverts a deliberate upstream anti-steamroller message.**

Base (and current main) reads:
```
"%w: %s is held by %s; coordinate with the holder — pass --force only if their claim is abandoned (crashed agent, expired lease)"
```
The PR shortens both sites to `"(use --force to override)"`. The long form is deliberate — the matching comment in `claim.go:155-160` names the incident (`wy-yuclk`: agents pattern-matching the terse message into an unclaim+claim steamroller of live claims). Restoring the original text costs nothing and removes two conflict hunks.

**S-6 — `internal/storage/issueops/unclaim.go:87`: `--if-fence` alone grants cross-actor release authority.**

```go
if force || hasGuard {
    ownerPredicate = "AND assignee != ''"
```
With any guard set, the `ErrNotOwner` check is skipped. `guard.go:17-23` justifies this as "the guard is the credential." That holds for `--if-assignee` (you must name the holder). It does **not** hold for `--if-fence` alone: the fence is a small integer, printed by `bd show`, not a secret. `bd unclaim X --if-fence 3` becomes a `--force` that any actor can perform with one read. A guard establishes *freshness*, not *authority* — those are different properties, and the code conflates them.

*Fix:* require `Guard.Assignee != nil` (or actor == assignee) to authorize a cross-actor release; let a fence-only guard add a precondition without lifting the owner check.

**S-7 — `internal/telemetry/storage.go`: silently drops instrumentation for `UnclaimIssueIfAssignee`.**

The PR deletes the `InstrumentedStorage.UnclaimIssueIfAssignee` wrapper. It still compiles (`InstrumentedStorage` embeds `storage.DoltStorage` as a passthrough at line 29), so this is a silent telemetry hole rather than a build break — which makes it easier to miss. Upstream still has the method. Nothing in this PR requires its removal.

## 1. Design assessment

### 1a. The whole-row CAS token duplicates one that already exists (and that this author shipped)

`internal/storage/storage.go:322` on main already defines `ExpectedVersion *int64`, backed by the `row_lock` column, surfaced to Go callers as `types.Issue.RowVersion`: an opaque random-per-write int64, compared for equality only, never ordered, with `storage.ErrVersionMismatch`, `issueops.CheckVersionInTx`, `UpdateIssueChecked`, and `CloseIssueChecked`. That surface landed in **#4911, by julianknutsen, merged 2026-07-22** — nine days after this PR's base.

This PR adds `revision`: an opaque random-per-write int64, compared for equality only, never ordered, with `storage.ErrPreconditionFailed`, `UpdateIssueIfMatch`, `CloseIssueIfMatch`. Two parallel whole-row tokens on the same two tables.

The only real semantic difference is stamping breadth: `row_lock` is stamped on lifecycle/ownership writes (status/assignee/started_at); `revision` is stamped on *every* content write. That difference is a one-line policy change to `freshRowLock()`'s call sites, not a reason for a second column, a migration, a second sentinel error family, a second CLI flag family, and a merge resolver.

**Recommended shape:** widen `row_lock`'s stamping to all content writes (keeping the documented `is_blocked`/heartbeat exemptions from `auxOrExemptMarkers`, which are genuinely good analysis), and expose the existing `RowVersion` as `--if-revision`. That deletes the migration, `internal/types/types.go:25`, `internal/storage/issueops/revision.go`, and most of the mergesettle work.

### 1b. The metadata-key CAS duplicates `MergeMetadata`, and regresses it

`internal/storage/dolt/slots.go:25` on main is `MergeMetadata` — also from #4911 — which does read+merge+write in one transaction with `withRetryTx`, routes through `UpdateIssueInTx` so it *records a full EventUpdated and runs the configured metadata-schema validation*, and handles wisp routing.

This PR replaces `SlotSet`/`SlotClear` with `issueops.SetMetadataKeyInTx`/`ClearMetadataKeyInTx` (`internal/storage/dolt/slots.go:19`, `internal/storage/embeddeddolt/slots.go`), which bypass both. The PR is rewriting a lost-update bug that main already fixed, and losing two properties in the process (see finding B4).

**The simpler alternative for `bd cas set/unset`:** add an `expected *string` / `ifAbsent bool` precondition to the existing `issueops.MergeMetadataInTx`. Same transaction, same retry loop, same validation and event, ~40 lines instead of ~250 plus a parallel `ConditionalWriter` metadata surface.

### 1c. The mergesettle work is fully superseded

Main landed `internal/storage/versioncontrolops/automerge.go` (34695bdb6 + f178de227, 2026-07-24): a general **field-level three-way merge** — a cell only one side changed keeps that side's value; a cell both sides changed is settled LWW by `updated_at`; add/add and delete/modify escalate. `resolveIssuesRevisionOnlyConflicts` in this PR is a narrow special case of exactly that rule. ~450 lines of this PR (mergesettle.go + `revision_merge_resolve_test.go` + `revision_merge_probe_test.go`) are now redundant.

**But one idea in it is genuinely new and worth absorbing**: `freshRevisionDistinctFrom` (`mergesettle.go`, new). Main's automerge settles a contested opaque token by LWW, so the merged row carries one side's *old* token — a client still holding it can win a CAS it should have lost. That hazard exists **today** for `row_lock`/`ExpectedVersion`, independent of this PR. A ~15-line special case in `automerge.go` (mint a fresh token distinct from both sides for any opaque concurrency cell) closes it. That is the highest-value idea in the PR.

### 1d. Charter layering

Layering holds. CAS on tracking primitives belongs in beads core; the PR keeps orchestration policy (fences, epochs, reservations) in the caller and only ships the primitive. No complaint here.

### 1e. Does this close #3575/#4657?

No. Those report `bd update --claim` not being a hard CAS under sub-second concurrency. This PR does not touch `--claim` — it explicitly *forbids* combining `--if-revision` with `--claim` (`cmd/bd/update.go:333`). What actually addresses that class is main's #5008 (`--if-assignee`/`--if-status`) plus #5006 (`verifiedClaimWrite`). This PR provides an adjacent, more general primitive; it should not be framed as closing those issues.

## 2. Correctness findings

### BLOCKERS

**B1 — Serializing `revision` violates the interchange protocol contract. CI proves it.**
`internal/types/types.go:25` — `Revision int64 \`json:"revision,omitempty"\``

`bd export` marshals `types.Issue` directly (`cmd/bd/export.go:222`), so every issue line in `.beads/issues.jsonl` now carries a fresh random 19-digit number that changes on every write. CI is red on exactly this:

```
--- FAIL: TestProtocol_Interchange_RoundTripEquivalence
    §J6.6 violated: export → import → export did not reproduce the stream
      original:  {..."revision":8994782090524358520,...}
      re-export: {..."revision":1263971878294177482,...}
--- FAIL: TestProtocol_Interchange_StdinImport
    §J6.5: stream imported from stdin did not re-export identically
```

plus `TestExportImportRoundTripE2E` (dolt-embedded **and** postgres) and 21 `TestConformanceE2E` subtests.

This is not an incidental golden-file update: the repo made the opposite decision deliberately for the identical token. `internal/types/types_test.go:942`, `TestRowVersionNeverSerialized`, locks in "row_lock is random per write, so serializing it would break stable bd list --json diffs and JSONL export churn." The PR body says "`bd show --json` already carries it" as if that were a feature; it is the regression.

**Fix:** drop the JSON tag (`json:"-"`), matching `RowVersion`. Surface the token via `bd show --long` only (which the PR already does at `cmd/bd/show_format.go:286`) or a dedicated `--revision` output. Do not regenerate the corpus to accept it.

**B2 — Import is no longer idempotent; every import dirties every row.**
`internal/storage/issueops/helpers.go:65` and `internal/storage/domain/db/issue.go:543`

`revision` was added to `issueUpsertColumns`, so the unguarded `ON DUPLICATE KEY UPDATE` path assigns `revision = VALUES(revision)` where `VALUES(revision)` is a fresh `NewRevision()` per statement (`insertIssueIntoTable`, `insertIssueRow`). Main's own comment three lines above states the invariant being broken: *"Re-importing an identical snapshot stays idempotent either way — the rewrite would have written identical values."*

Consequences: re-importing an unchanged JSONL rewrites every row, leaves the Dolt working set dirty, produces a spurious commit, and (because every row's revision moved) manufactures a cross-clone conflict on the next pull for every issue in the file. Compounding B1, the exported value is also *discarded* on import — `insertIssueRow` binds `issueops.NewRevision()`, not `issue.Revision` — so the field is pure write-only noise.

**Fix:** exclude `revision` from the upsert assignment set entirely (an import is not a content write to the CAS timeline), or bind `issue.Revision` and only mint when the incoming value is zero.

**B3 — Exit code 13 now means two contradictory things.**
`cmd/bd/if_revision.go:21` — `const ExitConditionalWriteUnsupported = 13`
vs. main `cmd/bd/update.go:642` — `const ExitGuardMismatch = 13`

Main shipped 13 as *"a racer won — skip gracefully, this is retryable."* This PR ships 13 as *"gate refusal — a caller must **not** retry it as if it were a race"* and puts the retryable case on 9. The two are semantically inverted on the same number. Any wrapper written against main's contract misreads this PR's output, and vice versa.

The PR's own audit comment (`cmd/bd/cas.go:16-18`, "Verified free: 1, 2, 10-12") is stale — it predates #5008. That staleness is how the collision happened, and it will happen again on the next rebase unless the codes are centralized.

**Fix:** on rebase, map `--if-revision`/`bd cas` mismatch to the existing `ExitGuardMismatch` (13) — semantically it *is* a guard mismatch — and allocate a new free code for the gate refusal. Add a single `exitcodes.go` registry so the next contributor can't collide.

**B4 — The guarded write paths silently drop validation and routing the unguarded paths perform.**
`internal/storage/dolt/conditional.go:78-90` (`UpdateIssueIfMatch`)

`DoltStore.UpdateIssue` (`internal/storage/dolt/issues.go:183`) does three things before delegating:
1. `validateUpdateMetadata(updates)` — metadata-schema validation (GH#1416 Phase 2)
2. wisp routing
3. `DemoteToWisp` when `no_history`/`wisp` is in the update set

`UpdateIssueIfMatch` does only (2), via `IsActiveWispInTx`. So:

- `bd update &lt;id&gt; --if-revision N --metadata '{...}'` writes metadata that bypasses the configured schema. Reachable: `cmd/bd/update.go:283` puts `--metadata` into `updates`, which flows into `regularUpdates` and then into the guarded call at `cmd/bd/update.go:462`.
- `bd update &lt;id&gt; --if-revision N --no-history` sets the `no_history` column in place instead of migrating the row to the `wisps` table. `no_history` is an allowed update field (`internal/storage/issueops/update.go:23`) and reachable from `cmd/bd/update.go:277`. Note CI's `TestConformanceE2E/update-no-history-demote` is red.

The same omission hits the slots rewrite: `internal/storage/dolt/slots.go:19` `SlotSet` now reaches `SetMetadataKeyInTx` directly, so `bd slot set` no longer validates against a configured metadata schema, and the recorded event payload changed shape (old `""` / new bare scalar, vs. the full old/new issue JSON `UpdateIssueInTx` records).

**Fix:** route the guarded writes through the same pre-flight as the unguarded ones (main's `UpdateIssueChecked` shows the pattern — validate, then `withConn`), or better, per §1a/§1b, don't add parallel entry points at all.

**B5 — The federation gate makes whole-row CAS dead on arrival for the normal beads topology, and is absent from the mode where it matters most.**
`internal/storage/dolt/conditional_gate.go:66-79`; `internal/storage/embeddeddolt/conditional.go:46-73`

`checkConditionalWriteGate` refuses whole-row CAS whenever *any* Dolt remote is configured. In beads, a configured remote is the documented normal state — `refs/dolt/data` sync via `bd dolt push`/`pull` is the architecture. So for essentially every real user, `bd update/close/assign/delete --if-revision` exits 13 unless they set `BD_ALLOW_UNSAFE_CAS=1`. Roughly half the PR's feature surface ships unusable by default, and neither `docs/cli-reference/cas.md` nor the `--if-revision` flag help mentions the gate or the env var (only the error string does).

Worse, the gate is applied **only in `DoltStore`** (server mode). `EmbeddedDoltStore` — the default local mode, and the one with a Dolt remote in every synced repo — implements `UpdateIssueIfMatch`/`CloseIssueIfMatch`/`DeleteIssueIfMatch` with no gate at all. The safety check is missing from exactly the deployment it was written to protect.

This is also self-contradictory within the PR: the gate's own doc comment says it fires *"until the revision-cell merge resolver lands"* — and the resolver is in this same diff.

**Fix:** decide one way. Either the resolver closes the hole (drop the gate, keep the resolver), or it does not (keep the gate and apply it in `embeddeddolt` too, and document the limitation prominently). Shipping both, inconsistently, is the worst option.

### SHOULD-FIX

**S1 — Migration number collision.** `internal/storage/schema/migrations/0055_add_revision.up.sql`. Main already has `0055_move_leases_to_table` and is at `0059`. Two different `0055_*` migrations. Renumber to `0060` and update `internal/storage/schema/cli_migrations.go` (which conflicts).

**S2 — The atomicity doc claim is wrong in one direction and self-contradictory in the other.** `internal/storage/issueops/conditional.go:44-48`: *"two concurrent writers necessarily write different values to the one metadata blob cell, so Dolt's cell-wise transaction merge forces a serialization conflict on all but one — no per-write nonce is required."* Two writers CAS-ing the same key to the **same** value produce a convergent cell write and would not conflict. Embedded Dolt's process-level file lock probably makes that safe, but nothing proves it. Add one multi-process test that shells the built binary.
